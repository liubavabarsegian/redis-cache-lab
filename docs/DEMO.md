# Сценарий видео уровня Э

Цель — показать код, фактическое снижение чтений, PATCH, конкурентные промахи и SWR за 3:40–3:50. Лимит задания — 4:00. Видео записывает автор работы; установку инструментов и сборку выполнить заранее.

## Подготовка вне записи

1. Убедиться, что Docker runtime работает. После его смены повторить весь набор; не использовать прежний результат как подтверждение нового окружения.
2. Сохранить реализацию в commit и записать `git rev-parse HEAD`. Отчёт должен честно указывать, с какими локальными изменениями выполнялась проверка.
3. Открыть `app/service.py`, `tests/test_additional.py` и терминал. Увеличить шрифт и убрать посторонние окна.
4. Подготовить образы и запустить все проверки:

```sh
docker compose build api tests
docker compose run --rm tests
docker compose run --rm tests python -m pytest -q tests/test_additional.py
FRESH_TTL=60 docker compose up -d --force-recreate api
curl --fail --retry 10 --retry-connrefused --retry-delay 1 http://localhost:8000/health
```

Ожидается 27 случаев в полном наборе и 5 в собственном файле. В ролике показывать полученный вывод, а не перепечатанные ожидаемые числа. Для демонстрации ниже API работает в `cache_aside`; экспертный тест сам создаёт сервис в `swr`.

Не читать `/products/1` до последовательного эксперимента: первый запрос должен быть холодным. `/health` и `/debug/stats` кэш товара не прогревают.

## Ход записи

### 0:00–0:40 — код и механизм

Показать hash и коротко открыть `service.py`:

```sh
git rev-parse HEAD
git status --short
```

Объяснить: JSON хранит товар и две временные границы; TTL задаётся атомарным SET PX; GET проверяет переданный `clock()`. PATCH обновляет источник перед DEL. Если DEL не удался, локальная dirty-отметка не позволяет вернуть старую цену.

### 0:40–1:10 — 20 последовательных запросов

```sh
docker compose exec -T api python scripts/measure.py
```

Показать `requests=20`, счётчики `before`/`after` и `source_reads_delta`. При свежем процессе и исправном Redis ожидается 0 → 1. Сопоставить с записанным в отчёте исходным измерением 0 → 20. Скрипт сам ожидает `/health` и проверяет ответы.

### 1:10–1:35 — изменение товара

```sh
curl --fail http://localhost:8000/products/1
curl --fail -X PATCH http://localhost:8000/products/1 -H 'Content-Type: application/json' -d '{"price_kopecks":55000,"stock":0}'
curl --fail http://localhost:8000/products/1
```

Показать новую цену, нулевой остаток и revision 2. Объяснить порядок «источник → инвалидация своего ключа».

### 1:35–2:00 — 20 конкурентных запросов

Нужен отдельный свежий процесс, чтобы прежний прогрев не скрыл stampede:

```sh
docker compose restart api
docker compose exec -T api python scripts/measure.py --concurrent
```

Скрипт ждёт готовность API. Показать 20 ответов и прирост чтений 1. Объяснить повторную проверку кэша под блокировкой товара и независимость разных ключей.

### 2:00–2:45 — SWR и гонка с PATCH

Запустить детерминированные сценарии с читаемыми названиями:

```sh
docker compose run --rm tests python -m pytest -v tests/test_expert.py::test_e1_stale_returns_before_a_single_background_refresh tests/test_expert.py::test_e3_update_cannot_be_overwritten_by_old_refresh
```

Показать в E1 блокировку источника и успешное завершение двух волн stale-читателей до освобождения refresh. Затем `wait_idle()` и новую запись. В E3 показать общий lock refresh/PATCH: старый refresh не записывает товар после завершившегося изменения. Это демонстрация SWR через тестовый сервис с управляемыми часами, а не через запущенный HTTP API.

### 2:45–3:15 — полный набор и собственный сценарий

```sh
docker compose run --rm tests
```

Показать фактический итог. Открыть собственный `test_failed_invalidation_preserves_other_product_cache`: ошибка удаления одного ключа не должна выключать кэш другого. Это новый сценарий, а не копия B5 с другой ценой.

### 3:15–3:45 — гарантии и ограничения

Кратко объяснить:

- свежая запись не запускает refresh;
- stale-окно ограничено, ошибка refresh не продлевает его;
- после hard expiry GET ждёт источник и не скрывает его ошибку;
- локальные lock и dirty-отметки действуют в одном процессе;
- при недоступности Redis чтений источника становится больше;
- финальную цену и наличие для покупки нужно проверять в источнике;
- `aclose()` отменяет фоновые задачи, Redis-клиент закрывает вызывающий код.

Если команды занимают дольше репетиции, сократить устные пояснения и показ деталей теста. Не превышать 4:00; при необходимости перезаписать ролик.

## После записи

- Записать ссылку и фактическую длительность в `REPORT.md` и описание PR.
- Убедиться, что ролик, результаты проверок и указанный hash относятся к одной реализации.
- Перед push проверить diff и отсутствие видеофайла, секретов и служебных каталогов в Git.
- Создать PR в `rbeketov/redis-cache-lab:main`; заполнить автора/группу, уровень Э, команды, результаты, ограничения и ссылку на отчёт.
